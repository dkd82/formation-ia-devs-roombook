TP Jour 2 · RoomBook : industrialiser avec l'IA Participants

RoomBook grandit. Aujourd'hui, vous passez d'un usage individuel de l'IA à un système d'équipe : un fichier de contexte partagé, des commandes réutilisables, des sous-agents spécialisés, des hooks qui garantissent les règles, une CI et une documentation à jour. Chaque ticket fait évoluer l'application et son outillage.

Durée totale : ≈ 3 h · Outils : GitHub Copilot (VS Code) et Claude Code (CLI)

Mise en route

Prérequis

  • Node.js 20+, Git, VS Code avec GitHub Copilot Chat, Claude Code en ligne de commande
  • Votre dépôt RoomBook de la veille, ou à défaut la branche jour2-start du dépôt de la formation (bug corrigé, annulation et 6 tests)
  • Un dépôt GitHub (pour la CI et la revue de PR) : poussez votre projet dessus

Étapes

  1. Repartez de votre dépôt, ou récupérez la branche de départ : git fetch origin puis git switch jour2-start.
  2. Installez : npm install puis npm --prefix backend install. Committez les fichiers package-lock.json générés (la CI utilisera npm ci).
  3. Vérifiez : npm test (6 tests verts au minimum) et npm run lint (aucun avertissement).
  4. Créez une branche par ticket : git switch -c j2-ticket-1, etc.
L'anatomie d'un bon prompt
Contexte
Où en est-on ? Techno, fichiers, situation.
Tâche
Quel objectif précis et unique ?
Contraintes
Style, limites, ce qu'il ne faut pas toucher.
Critères de succès
Comment saura-t-on que c'est réussi ?

Règles de travail

  • Le prompt reste structuré en 4 blocs : contexte, tâche, contraintes, critères de succès.
  • Les fichiers de configuration créés (commandes, agents, hooks) sont du code : relisez-les et committez-les.
  • Un hook s'exécute avec vos droits : ne copiez jamais un hook que vous n'avez pas lu.
  • Tout ce que l'IA affirme sur une commande ou une option doit être vérifié en l'exécutant.
Aide-mémoire des outils

GitHub Copilot (VS Code)

  • Modes de Chat : Ask (questions), Edit (modifications ciblées), Agent (tâches multi-fichiers avec exécution)
  • Contexte : #file:chemin, #codebase, #selection
  • Commandes : /explain, /fix, /tests
  • Personnalisation : .github/copilot-instructions.md, .github/prompts/*.prompt.md, .github/agents/*.agent.md

Claude Code (CLI)

  • Démarrer : claude à la racine du projet ; citer un fichier : @chemin
  • Mode plan : Shift+Tab ; contexte : /clear, /compact, /cost, /context
  • Configuration : /init, /memory, /agents, /hooks, /help
  • Personnalisation : CLAUDE.md, .claude/commands/, .claude/agents/, .claude/settings.json

Les interfaces évoluent vite : en cas de doute, vérifiez dans la documentation de la version installée.

J2-1

Le fichier de contexte partagé

Durée : 20 minOutil : Claude Code + CopilotNiveau : Facile

Le ticket

Chaque développeur redonne les mêmes explications à son assistant. L'équipe veut un fichier de contexte unique, versionné, lu par Claude Code et par GitHub Copilot.

Critères d'acceptation

Prompt de génération du fichier de contexte

Complétez chacun des quatre blocs dans la zone ci-dessous, puis copiez le prompt et collez-le dans le chat de votre outil.

ContexteOù en est-on ? Techno, fichiers, situation.
Quel projet, quelles technos, quels assistants doivent partager ces règles ?
TâcheQuel objectif précis et unique ?
Quel fichier créer, avec quelles sections ?
ContraintesStyle, limites, ce qu'il ne faut pas toucher.
Longueur, fiabilité des commandes, ce qu'il ne faut pas y mettre.
Critères de succèsComment saura-t-on que c'est réussi ?
Qu'est-ce qu'un nouvel arrivant (ou un agent) doit pouvoir faire seul ?

Conseils par outil

GitHub Copilot (VS Code)

  • Créez .github/copilot-instructions.md avec le contenu d'AGENTS.md (selon la version de VS Code, AGENTS.md peut aussi être pris en compte : vérifiez les paramètres).
  • Contrôle : une réponse de Chat doit mentionner ces règles ; sinon, regardez les « références » listées sous la réponse.

Claude Code (CLI)

  • /init génère un CLAUDE.md initial : comparez-le avec votre prompt.
  • Dans CLAUDE.md, écrivez simplement @AGENTS.md pour importer le fichier partagé. Vérifiez avec /memory.

Vérifier avant de passer au ticket suivant

  • Exécutez chaque commande listée dans AGENTS.md.
  • Nouvelle session Claude Code : « Comment lancer les tests ? » doit répondre juste sans explorer.
  • Le fichier fait 60 lignes ou moins.

J2-3

Commande /review partagée (slash command et prompt file)

Durée : 20 minOutil : Claude Code + CopilotNiveau : Moyen

Le ticket

Les revues de code ne suivent pas toutes la même checklist. Créez une commande de revue réutilisable, en lecture seule, disponible dans Claude Code (/review) et dans Copilot (prompt file).

Critères d'acceptation

Prompt de création de la commande

Complétez chacun des quatre blocs dans la zone ci-dessous, puis copiez le prompt et collez-le dans le chat de votre outil.

ContexteOù en est-on ? Techno, fichiers, situation.
Pourquoi cette commande ? Pour quels outils ? Quel document de référence ?
TâcheQuel objectif précis et unique ?
Quels fichiers créer, où, pour chaque outil ? Quel argument ?
ContraintesStyle, limites, ce qu'il ne faut pas toucher.
Droits minimum ? Frontmatter ? Taille ? Ordre de la checklist ?
Critères de succèsComment saura-t-on que c'est réussi ?

Conseils par outil

GitHub Copilot (VS Code)

  • Un prompt file se déclenche dans Chat avec /review. Selon la version de VS Code, le frontmatter utilise agent ou l'ancien mode : (ask suffit pour une lecture seule).
  • Utilisez ${input:cible} pour passer un argument.

Claude Code (CLI)

  • Le nom du fichier devient le nom de la commande. Rechargez la liste avec /help.
  • L'argument se récupère avec $ARGUMENTS dans le corps du fichier.

Vérifier avant de passer au ticket suivant

  • Tapez /review dans chaque outil : la commande apparaît.
  • Introduisez une clé API fictive en dur dans un fichier, committez sur une branche de test, relancez /review : le problème doit être remonté en tête.
  • git status après la revue : aucun fichier modifié par la commande.

Vérifier avant de passer au ticket suivant

J2-5

Garde-fous : hooks Claude Code et hook Git

Durée : 30 minOutil : Claude Code (hooks) · Git (pour Copilot)Niveau : Avancé

Le ticket

L'équipe veut des règles qui s'appliquent à coup sûr, sans dépendre de la bonne volonté du modèle : formatage automatique, protection des secrets et des commandes destructrices, interdiction de conclure avec des tests rouges. Copilot n'utilise pas les hooks de Claude Code : un hook Git commun sert de filet.

Critères d'acceptation

Partie A · Hooks Claude Code

Complétez chacun des quatre blocs dans la zone ci-dessous, puis copiez le prompt et collez-le dans le chat de votre outil.

ContexteOù en est-on ? Techno, fichiers, situation.
Quel risque voulez-vous couvrir ? Pourquoi un hook plutôt qu'une consigne ?
TâcheQuel objectif précis et unique ?
Listez chaque hook avec son événement, son matcher et son effet.
ContraintesStyle, limites, ce qu'il ne faut pas toucher.
Portabilité (Windows) ? Convention de blocage ? Risque de boucle ? Performance ?
Critères de succèsComment saura-t-on que c'est réussi ?
Comment démontrerez-vous chacun des 3 hooks ?

Partie B · Hook Git commun (filet pour tous les outils)

Complétez chacun des quatre blocs dans la zone ci-dessous, puis copiez le prompt et collez-le dans le chat de votre outil.

ContexteOù en est-on ? Techno, fichiers, situation.
Pourquoi un hook Git en plus ? Qui n'est pas couvert par les hooks de l'agent ?
TâcheQuel objectif précis et unique ?
Quel hook, où, avec quelles vérifications ?
ContraintesStyle, limites, ce qu'il ne faut pas toucher.
Compatibilité, dépendances, documentation ?
Critères de succèsComment saura-t-on que c'est réussi ?
Quels cas testez-vous (refus, acceptation, durée) ?

Conseils par outil

GitHub Copilot (VS Code)

  • Les hooks de session de Claude Code ne s'appliquent pas à Copilot : c'est le rôle du hook Git de la partie B.
  • Certaines versions de VS Code proposent des hooks d'agent en préversion : vérifiez la documentation de votre version avant de vous y fier.

Claude Code (CLI)

  • /hooks affiche la configuration active. Les hooks s'appliquent à la session suivante ou après rechargement.
  • Pour tester le blocage, demandez volontairement l'action interdite et lisez le message renvoyé à l'agent.

Vérifier avant de passer au ticket suivant

  • Démonstration des 3 hooks Claude Code (a, b, c).
  • git commit avec un test cassé : refusé.
  • Créez un fichier .env factice : le commit est refusé, mais .gitignore l'ignore déjà (testez avec git add -f).
